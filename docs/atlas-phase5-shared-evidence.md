# ATLAS 5.1A — isolated shared document evidence

This is a deliberately disabled-by-default pilot, not an automatic migration, deployment, or completion of all Phase 5.1. It supports explicitly publishing one dated public document observation at a time and server-confirmed, paginated reads from another authorized device. Existing browser-local facts and account data are unchanged. Only source-native registry identities without a duplicate in the loaded directory qualify; legacy account reconciliation is still required. No shared evidence is fed into scoring or the map until conflict, correction, revocation and completeness semantics are designed. No notes, contacts, pipeline, attachments or identity review records are uploaded.

## Provisioning (administrator, separate project only)
1. Create an independent company-approved Firebase project; enable Google authentication, configure authorized domains for the deployment, and create its default Firestore database. Do not reuse the legacy app's Firebase project. Confirm IAM, data retention and approval to share public document observations. Configure the app's publicly visible client config and restrict authorized domains; never expose admin credentials.
2. Deploy **only** `security/atlas-evidence.firestore.rules` to the separate project, using the Firebase console or a dedicated Firebase CLI config targeting that project's default database. Never replace the existing agency application's rules. Verify deny-by-default in the actual project, not just the source file. The rule set has no other client access paths.
3. Using an authorized administrator's tooling, create `workspaces/{workspaceId}/members/{uid}` with role `viewer` or `editor` for each approved verified Google identity. Users cannot grant themselves roles. Revoke access by removing the member document. Keep admin access separate. No public collection, anonymous access, client-side membership writes, edits or deletes. Authorized administrators can still change data through IAM; govern and audit those privileged actions.
4. Only after validating the above, configure the frontend build's VITE_ATLAS_EVIDENCE_ENABLED=true, VITE_ATLAS_EVIDENCE_API_KEY, VITE_ATLAS_EVIDENCE_AUTH_DOMAIN, VITE_ATLAS_EVIDENCE_PROJECT_ID, VITE_ATLAS_EVIDENCE_APP_ID and VITE_ATLAS_EVIDENCE_WORKSPACE_ID. These are public client configuration, not secrets. Rebuild and publish the integrated app. Remove the enable flag to disable the feature. A missing/invalid configuration or same legacy project blocks the UI.
5. Reports & intelligence > ATLAS shared evidence. Open, authenticate, select a source-native account, refresh shared records. Editors may preview and explicitly authorize one local document; viewer accounts cannot publish. Test on desktop and installed PWA. Sign-out clears the mounted shared list; authentication and records use memory only. Reopening the workspace may reuse the in-memory signed-in session until sign-out or reload. Server queries are bounded to 50 and never claim complete opportunity coverage.

## Required staging acceptance before enabling
Test actual rules in an emulator and the new staging project: anonymous/unverified/wrong-project/nonmember and revoked member denied; viewer read/list allowed but writes denied; editor valid create allowed; author/timestamp forgery, cross-workspace reads, wrong path identity, oversized/unknown fields, invalid kinds and unbounded queries denied; update/delete denied; identical retry no duplicate; changed ID contents conflict; failed/offline write never reports success; server-only read fails offline, not a cached success; two users and two devices can see acknowledged evidence; sign-out and account switching clear displayed shared data. Client validation is not a replacement for authorization; server rules check access and record shape, not the truth of documents or every semantic/date constraint. The pure client tests do not establish deployed security.

## Remaining phase work

## Phase 5.1C — read-only document reconciliation
A review panel in the shared workspace compares published observations with typed local evidence for the selected registry identity. It collapses equivalent observations for review only; immutable record ID conflicts retain both payloads. It identifies latest-date equipment disagreements, older and stale observations, issuer-scoped procurement closures/awards, ambiguous reopenings, elapsed deadlines, and contract/funding discrepancies. It does not infer replacement, current ownership, verified coverage, or shared approval. Local flags are shown as local review requirements, never as shared decisions. Records from different issuers are not conflated; source authenticity and record scope still require human review.
Account-wide classification is allowed only for a confirmed server read of the first page with fewer than 50 records, no withheld/invalid typed evidence, and an eligible account. Exactly 50 or any subsequent page is incomplete, even if it happens to be the last page. Reconciliation never promotes data to Radar, the map, provider fields, or cloud state. No persistent correction/revocation event workflow has been added yet. The new panel has unit tests for the pure reconciliation logic; live user/device validation and an administrator-approved activation remain outstanding.

## Phase 5.1D — permanent review governance
A separate administrator-assigned `reviewer` role can read evidence and record permanent, fixed-ID review decisions on an existing published document. Editors publish; reviewers review; viewers read. Reviewers cannot publish or approve their own authored evidence even after a role change. A source approval is a human review assertion, not independent verification of the underlying fact. Challenge, withdrawal and supersession are irreversible blocking decisions and take precedence over approval. Correcting a record means publishing a new immutable document observation, independent approval of that replacement, and a reviewer linking the original to it. Funding, procurement and contract replacements must retain the same issuer and record ID; all replacements must match the agency, state and evidence kind. An approved but subsequently blocked replacement cannot qualify as reviewed. Original evidence remains available for authorized audit; withdrawal is not deletion or privacy erasure. A privacy concern must be escalated to the authorized data administrator for actual remediation.

The schema uses at most four immutable decision documents under each evidence record. Rules reject self-approval, forged actors/timestamps, unknown reason codes, direct edits/deletes, cross-workspace writes and cyclic supersession. Only an administrator with approved IAM can change roles. The role is exclusive; a reviewer must not self-publish or grant membership. UI reads decision history from the server for a selected evidence record; it cannot certify a whole territory. A replacement may be selected from the loaded evidence page. The independent reconciliation panel remains research-only, and no approval is automatically imported into the Opportunity Radar, equipment map, or sales scores. The existing feature enablement and separate-project staging checks still apply. Deploy updated evidence rules only to the dedicated staging project after emulator tests pass; do not replace the legacy agency rules. No live project was provisioned or altered.

## Phase 5.1E — reviewed shared Opportunity Radar
The selected-account shared workspace now has an explicit Evaluate reviewed opportunities action. It reads the first page of published evidence and checks every decision history twice, with six concurrent reads at a time. A second evidence read detects changed records. Incomplete pages (50 or more), invalid history, conflicting reads, loss of authorization and network errors fail closed. This is a bounded, non-atomic sampled review, not a live or transactional territory snapshot. The browser clears results on account change, local publication or review action, offline events and after five minutes. No shared results persist locally.

Only independently approved, currently unblocked, reconciled observations produce research signals. Pending and challenged/withdrawn observations remain contextual blockers so newer negative evidence cannot resurrect older opportunities. Equivalent duplicate observations require approval of all active published copies. Superseded originals are omitted only when their matching correction chain ends at an approved, unblocked document; broken/cyclic/missing chains suppress the account's entire review. Local facts and notes are deliberately excluded from this shared-only calculation. The engine uses existing freshness rules, a 365-day upcoming contract horizon and documented procurement dates. It withholds ambiguous same-number solicitations from different issuers, mixed vendor values and unknown equipment brands. Signals provide source, reviewer, published document date and next verification action. No scores, forecasts, market share or pipeline value are manufactured.

The shared Radar remains isolated from the existing local Radar, competitive equipment map and operational agency records. Access is still behind the separate-project feature flag. Production activation, end-to-end device testing, larger-account pagination and territory-wide coverage need separate validation. This PR changes no production data or Firebase rules.

## Phase 5.1F — reviewed competitive equipment mapping
The GIS territory workspace and Google Maps workspace expose an explicit reviewed equipment map entry when the separate evidence feature is enabled. It reuses the authenticated member gate, source-reviewed Radar validation and bundled Census county outlines; it does not inject private shared observations into normal map data, saved agency records, exports, or local scoring. A user selects one state and at most five unique source-native accounts and starts a server check. Each account uses the bounded two-pass decision review (fewer than 50 records); server failures and incomplete review are unavailable, not unknown or competitor. Membership is checked before and after the sample. Results are memory-only, scoped to the selected identity fingerprints and expire five minutes after sampling starts; offline events invalidate them.

Reviewed equipment observations use the same independent approval, correction-chain, conflict, duplicate and freshness gates as the shared Radar, including recognized ZOLL observations. Multi-vendor strings and unknown makers do not produce positive classifications. Product categories can be filtered without additional server reads. Map colors distinguish ZOLL observed, other maker observed, both observed in the sample, no eligible recognized observation, review unavailable and not checked. County color is not a fleet statement or market share. Mixed may reflect different agencies or categories. Unmapped records are retained in the selected-account list; only a source-native county FIPS that matches a single reference county in the same state and does not conflict with the saved county or headquarters state can be plotted. No coordinates, name guesses, city centroids or service-area fan-out are used. Boundary loading failure withholds shapes rather than inventing assignments.

This is a deliberately limited research sample, not a nationwide completed census or an all-county bulk backfill. No shared results are persisted or copied to the existing equipment map. Live staging authentication, devices, source coverage, larger account pagination and bulk discovery remain outstanding. Production project/rules/data are unchanged.

Set ATLAS_SAM_DISCOVERY_ENABLED=true, ATLAS_SAM_API_KEY, ATLAS_SAM_GATEWAY_TOKEN (distinct random 32+ character URL-safe secret), and ATLAS_SAM_DAILY_LIMIT (default 8, configure at or below approved quota). The budget is process-local, not durable across restarts/replicas; production needs a shared rate limiter and approved gateway before activation. ## Phase 5.4A — explainable opportunity prioritization
The existing Reports & intelligence Opportunity Radar is now an account-level, deterministic research queue rather than a flat list of signals. The engine indexes IDs and native registry keys globally in linear passes, rejects duplicated/ambiguous identities before state filtering, and evaluates only rows with typed evidence via the existing provider competitive profile's local document reconciliation. Incomplete evidence blocks ranking; contradictory, stale, flagged, closed, superseded and history-only observations cannot contribute. Case/spacing-variant record identities for the same issuer and kind/lifecycle are withheld as ambiguous. Semantic duplicate observations do not increase urgency. No legacy estimates, public discovery candidates, unverified supplier matches, revenue, grant amounts, account size, activity scores, shared cloud approvals or inferred equipment enter ranking. Recognized competitor references require one maker and a category-compatible product mention, never generic or mixed-brand text.
Transparent priority bands: verify now = published solicitation response date 0–14 days away; verify soon = solicitation 15–45 days or documented contract end 0–90 days; plan research = later eligible solicitation, contract end 91–365 days, recent local grant/capital documents; explore = recognized competitor equipment reference or recent awarded procurement. UTC calendar days are used, not an exact deadline time; confirm timezone and current status. Equipment freshness 730 days, purchasing/funding 365 days; contract documents must also be at most 365 days old and end date within the next 365 days. The strongest eligible signal sets the account band, with dates, signal type, document date and stable identity used to break ties. Signal filters recompute priority based on matching evidence. No point accumulation, conversion prediction, AI model or financial opportunity scoring. Multiple unrelated observations are not assumed to concern the same purchase. Source links, reasons, next questions, evidence gaps, and explicit review cautions are shown. Counts are loaded rows/native identities, not market share, and review gaps can overlap rankable accounts. No server calls, persistence, automatic assignment, new backend or production changes. Seven domain tests and one SSR test cover timing, duplicates, conflict/lifecycle, source identity, filters, coverage and empty rendering. Production deployment and actual data coverage remain outstanding.
